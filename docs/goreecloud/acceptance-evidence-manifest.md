# GoreeCloud Network Acceptance Evidence Manifest

## Purpose

Formal GoreeCloud Network staging evidence must identify the exact source and immutable artifacts that were evaluated. A passing screenshot, log excerpt, or test note is not sufficient when it cannot be tied back to a specific control-plane revision, dashboard revision, container digest, and configuration state.

`deploy/goreecloud-staging/acceptance_evidence.py` creates a sanitized machine-readable manifest for that purpose. The manifest is evidence metadata only. It does not authorize production migration.

## Evidence identity requirements

Before formal evidence is collected, the staging `.env` must identify:

- the exact 40-character GoreeCloud Network control-plane source SHA;
- the exact 40-character GoreeCloud Network dashboard source SHA;
- immutable `image@sha256:<digest>` references for management, signal, relay, dashboard, and coturn;
- the rendered staging management and TURN configuration generated by the repository harness.

When Android acceptance is part of the run, also identify:

- the exact 40-character Android client source SHA;
- the SHA-256 of the APK or AAB actually used for the acceptance run.

The collector fails closed when a formal image reference is tag-only, when a source SHA is malformed, when required Android evidence is missing, when the checked-out control-plane repository does not match the declared control-plane SHA, or when the required rendered configuration is absent.

## Sanitized output

The generated manifest records only whitelisted evidence fields:

- evidence schema version;
- collection timestamp;
- environment classification;
- control-plane and dashboard source SHAs;
- optional Android source and artifact hashes;
- immutable image references and their SHA-256 digests;
- SHA-256 values for `compose.yaml`, rendered `management.json`, and rendered `turnserver.conf`;
- non-secret runtime metadata such as platform, Python, Docker, and Docker Compose versions when available;
- explicit assertions that credentials are not included and production migration is not authorized.

The collector does not serialize the populated `.env`, OIDC client secrets, datastore encryption keys, relay secrets, TURN passwords, tokens, setup keys, private keys, or other reusable credentials.

## Collection workflow

After the normal staging render and validation steps pass:

```sh
cd deploy/goreecloud-staging
python3 acceptance_evidence.py collect
```

For a run that is intended to include Android acceptance evidence:

```sh
python3 acceptance_evidence.py collect --require-android
```

The default output is:

```text
deploy/goreecloud-staging/runtime/acceptance-evidence.json
```

The `runtime/` directory is ignored by Git. Preserve the generated manifest with the controlled acceptance record rather than committing runtime evidence to the source branch.

## Relationship to acceptance

A manifest proves artifact identity and configuration identity. It does not prove that enrollment, policies, routing, DNS, relay behavior, dashboard workflows, Android connectivity, backup/restore, or rollback succeeded.

The manifest must therefore be retained alongside the results required by `isolated-acceptance-plan.md` and `rollback-and-recovery-plan.md`.

Production migration remains prohibited until the complete GoreeCloud Network acceptance criteria are satisfied and a separate production migration decision is approved.
